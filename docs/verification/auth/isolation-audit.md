# 用户隔离破坏性测试

测试在临时 SQLite 数据库运行，包含独立管理员、两位教师及两组班级/学生样本；未向线上发送破坏性请求。复现命令：PowerShell 中设置 `$env:SAKURA_AUDIT_ISOLATION='true'`，运行 `npm run test:sqlite`。测试针对期望隔离规则断言，当前预期以失败退出。

2026-10-28 的结果：原有 38 项回归通过；新增隔离场景 2 项通过、3 项失败。

1. 管理员通过教案列表查询到了另一位教师标记为 private 的教案：HTTP 200，返回 1 条。新需求不允许 root 看到隔离内容。
2. 管理员通过 SQLite 控制台 SELECT 查询私人教案正文：HTTP 200；全库 SQL 和数据库备份同样需要纳入权限设计。
3. 为另一名教师分配同一班级后，该教师可列出该班级的另一教师作业。现有边界是班级，而不是用户。
4. 两名不同班级的普通教师之间，私人教案列表未泄露：通过。初始测试教师可建立私有教案：通过。

代码审查还发现现有云端请求都进入同一个 school Durable Object；初始化预置 admin，新注册用户固定为 teacher，尚未实现空库首位注册者为 root。现有共享课程、学籍、考试、家校、工作台、备份与管理员功能均需重新设计隔离边界。尚未实现或验证 key 相互确认，也未对真实生产数据执行越权或清除操作。上述测试通过项不足以证明其他接口安全，不可据此判断已达到推广条件。
