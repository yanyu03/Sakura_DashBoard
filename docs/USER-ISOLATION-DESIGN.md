# SakuraEdu 用户隔离与 Key 授权方案（待实施）

## 目标和当前状态

- 一个首次开机注册的 root，只管理用户目录、账号状态和授权关系；不得通过应用读取、搜索、导出或备份其他账号的私人内容。
- 用户拥有独立数据。主任、辅导员、导师、教师、家长、学生等是业务身份，不自动获得其他人的数据权限。用户名创建后不可更改；姓名可选。
- 所有跨账号确认、报送和接收都基于双方确认的 Key 授权；默认禁止跨账号读取。身份确认不等于共享所有数据。
- 当前云端单个 `school` Durable Object 保存全部数据。现有逻辑对管理员放行、按班级共享，与目标不符。当前仅在本地关闭了 SQLite 管理接口、调整控制台，尚未形成完整隔离，也未部署。

## 已核实的问题

隔离测试记录：`docs/verification/auth/isolation-audit.md`。隔离数据库里复现了管理员看到私人教案、管理员 SQL 查询私人正文、同班教师读到彼此作业；普通教师跨班访问私人教案被拒绝。现有 38 项回归主要验证同校协作，不代表个人隔离通过。

代码审查还发现：

1. 管理员在 `classAccess`、教案、关怀、工作台等路径中存在广泛放行；数据列表、详情、修改、搜索、统计和通知都需检查。
2. 学生、班级、课程、成绩及其子表大多以班级或父记录关联，缺少统一的用户数据域；给少数表增加 `owner_id` 不能覆盖导出、历史版本、关联查询和缓存。
3. 本地与云端此前提供全库查询、状态或备份。当前本地中间件已禁止 SQLite API；线上旧版本仍须视为存在该入口。新方案的个人数据导出必须限制到本人数据域，不提供跨用户全库导出或任意 SQL。
4. 现有注册只创建 teacher，云端初始化预置 admin；两者均不符合首次注册 root。姓名和用户名要求需要覆盖注册、资料更新与后端校验，不能只限制输入框。
5. 家长、学生等目前没有完整的账号角色及确认关系。现有关怀信息为站内记录，不应视为真实家长已验证或已送达。
6. 既有 Key 字段如请求幂等键并非身份凭证，也不是授权关系；不能复用它们授予数据访问权限。

## 建议的数据与身份边界

采用“中央身份目录 + 每个用户独立数据域”。云端每名用户使用单独 SQLite-backed Durable Object；本地使用独立的用户 SQLite 文件，并用独立身份目录保存账号、会话、角色和授权元数据。无需以用户提供的用户名或 Key 直接拼接文件路径或作为可信对象 ID；由服务端映射不可预测的内部 ID。

中央目录只持有账号标识、密码哈希、状态、用户可见的公开资料，以及必要的关系和授权元数据；不存放教学正文、学生档案或报送内容。所有业务请求先验证服务端会话，再由服务端确定当前用户的数据域；忽略客户端提交的 `user_id`、角色和数据域标识。root 的用户列表只返回约定的账号元数据，不返回密码哈希、Key、私人数据或未授权的报送内容。

每个域对业务记录及其子记录、附件、通知、搜索索引、统计和导出采用相同边界。默认无跨域业务查询；管理员不是隐式例外。用户可以独立创建和维护自己的数据。多人协作需要另行显式授权，不因相同班级、职务或显示名称而自动获得访问权。

这保证应用及其 API 的访问隔离；拥有服务器、数据库或备份底层访问权的运维人员是否也无法读取，取决于另行设计的加密与密钥管理，当前方案不声称端到端加密或抵御底层运维访问。

## 首次启动与账号

1. 新实例为空目录、空用户数据域，取消默认 admin 和演示业务数据。首个成功注册通过单个事务原子地获得 root；其他并发注册只能成为普通账号。采用单独的一次性初始化凭据限制首次 root 注册，避免公网被陌生人抢先注册；凭据由部署操作者安全保存，使用后失效。
2. 用户名归一化后唯一、不可修改；邮箱按当前产品需求作为登录标识，但未实现邮件验证和找回前，不作为可靠身份凭据。姓名允许为空，展示时可回退用户名，不能把回退值误认为真实姓名。
3. 角色由服务端管理，注册请求中的 role 一律不可信。默认新账号为普通用户，后续角色分配与真实身份核验分开；给学生或家长的授权不得仅凭自选角色生效。
4. 遵照用户要求移除旧版作为首次开机版本：先盘点并生成可验证的恢复快照，在隔离环境演练新实例，再切换。是否保留、删除旧云数据及备份按用户此前“移除旧的”要求实施，但必须先明确实际受影响范围和恢复点；不能在启动或迁移时静默清空。

## Key 与上报：保守默认语义

本方案暂将 Key 设计为**建立一对一确认关系的短期邀请凭证**，不是长期万能密码：用户 A 生成单次随机 Key，用户 B 提交后，A 在登录状态下看到 B 的账号及拟建立的关系并确认；服务端保存 Key 哈希、有效期、用途和状态，不记录明文，不放入 URL、日志或通知。未确认、过期、撤销、重复使用均拒绝；限制生成和验证频率。

确认关系本身不开放双方私人数据。报送需要发起人选择具体对象、接收者和最小字段，显示预览后确认；接收者只能看到被报送的快照和必要的发送者标识。未经报送的数据、历史版本、底层文件和其他学生记录不可读。接收者继续转发或导出默认关闭；撤销关系阻止未来报送，但已送出的快照是否撤回、保留多久应在发送前明确，不承诺能抹去已经复制的内容。

Key 和关系应支持过期、单次核销、双向解除、被撤销后立即拒绝新访问、审计生成/确认/报送/撤销事件。审计仅保存操作者、对象 ID、动作、结果和时间，不存 Key 明文或私人正文。若用户期望 Key 用作长期授权、自动同步或允许对方直接读取原始数据，需要先调整这部分语义，不能悄然扩大访问范围。

## 角色的最低权限

| 身份 | 默认能力 | 可跨账号接收的内容 |
| --- | --- | --- |
| root | 查看用户目录和状态、管理账号/角色 | 只有本人作为接收者且得到明确报送的内容；不因 root 自动读取 |
| 主任、辅导员、导师、教师 | 管理本人数据，按明确关系选择报送 | 已确认关系下具体授权的报送快照 |
| 家长、学生 | 查看本人数据及明确发给自己的内容 | 仅验证关系并针对本人授权的内容；不自动访问班级全体 |

角色只提供可用功能的上限，具体每条记录仍受数据域、关系、内容范围、有效期与撤销状态共同约束。未经确认的账号均无跨用户权限；不可由用户自选“主任”直接获取任何额外数据。

## 按顺序实施

1. 制定新身份目录和独立数据域 schema，设计一次性初始化和数据恢复流程；提供迁移/切换演练。禁用任意 SQL、全库状态和全库导出，并移除前端相关入口。
2. 完成首位 root 的原子注册、用户名不可修改、姓名选填、会话生命周期与并发初始化测试。root 用户列表仅返回安全元数据。
3. 将教案、作业、学生、考试、课表、关怀、通知、搜索及导出逐模块迁至本人数据域，拒绝客户端伪造域 ID；未迁移模块默认关闭，不能沿用管理员或同班放行。
4. 加入 Key 邀请、确认、撤销和事件审计；以具体对象和字段为单位实现报送快照及接收箱，默认禁止透传原始域。
5. 实现各角色的身份/关系授权和用户界面；恢复适配后的本地功能面板。每完成一个模块先测拒绝路径，再开放功能。
6. 在临时本地 SQLite 和隔离的 Workers 环境运行破坏性测试，完成上线清单后才部署；正式环境采用独立实例切换，不在真实用户数据上运行写入测试。

## 上线验收

- 首次并发注册只有一个 root；已有实例不会自动重置，用户名更新 API 拒绝修改。
- 对 root、每种普通角色、未登录用户、已撤销/过期账号，逐一对其他人的列表、详情、嵌套对象、增删改、搜索、统计、通知、附件、导出和直接猜测 ID 测试，均默认拒绝；本人数据正常使用。
- 同班或同名用户默认隔离；任意提交角色、域 ID、owner ID、路径和查询条件都不能绕过。原 SQL、全库备份和重置 API 对所有账号返回拒绝。
- Key 不得明文出现在持久存储、日志、通知、URL、备份或错误响应中；测试猜测、过期、重放、并发核销、撤销及限流。单纯确认关系不能访问私人数据。
- 报送仅到指定接收者，字段与预览一致；非接收者、撤销后新请求、重放和越权转发均失败。审计日志不含内容或凭证。
- 本地与 Workers 端执行同样的隔离矩阵；验证重启、故障中断和备份恢复后的边界，检查无线上演示账号或旧数据误恢复。回归正常业务、注册登录和可访问性。
